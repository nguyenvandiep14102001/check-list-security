# SQL Injection

## Tóm tắt 

Kẻ tấn công có thể sử dụng SQL injection trên một ứng dụng nếu ứng dụng đó có các truy vấn cơ sở dữ liệu động sử dụng nối chuỗi và đầu vào do người dùng cung cấp. Để tránh các lỗi SQL injection, các nhà phát triển cần:
- Dừng viết các truy vấn động nối chuỗi.
- Ngăn chặn dữ liệu SQL độc hại được đưa vào các truy vấn đã thực thi.
Có những kỹ thuật đơn giản để ngăn chặn lỗ hổng SQL injection và chúng có thể được sử dụng với hầu như bất kỳ loại ngôn ngữ lập trình và bất kỳ loại cơ sở dữ liệu nào. Mặc dù cơ sở dữ liệu XML có thể có các vấn đề tương tự (ví dụ: XPath và XQuery injection), các kỹ thuật này cũng có thể được sử dụng để bảo vệ chúng.

## Phòng tránh 
- Option 1: Sử dụng các câu lệnh đã chuẩn bị (với các truy vấn tham số)
- Option 2: Sử dụng các Stored Procedure được xây dựng đúng cách
- Option 3: Xác thực đầu vào danh sách cho phép
- Option 4: RẤT KHÔNG NÊN: Thoát khỏi tất cả dữ liệu đầu vào do người dùng cung cấp

### Defense Option 1: Các câu lệnh đã chuẩn bị (có truy vấn tham số)

Khi các developer được dạy cách viết truy vấn cơ sở dữ liệu, họ nên được hướng dẫn sử dụng các câu lệnh đã chuẩn bị với ràng buộc biến (hay còn gọi là truy vấn có tham số). Các câu lệnh đã chuẩn bị dễ viết và dễ hiểu hơn các truy vấn động, và các truy vấn có tham số buộc developer phải xác định tất cả mã SQL trước và truyền từng tham số vào truy vấn sau.

Nếu truy vấn cơ sở dữ liệu sử dụng kiểu mã hóa này, cơ sở dữ liệu sẽ luôn phân biệt giữa mã và dữ liệu, bất kể người dùng cung cấp đầu vào nào. Ngoài ra, các câu lệnh đã chuẩn bị đảm bảo rằng kẻ tấn công không thể thay đổi mục đích của truy vấn, ngay cả khi kẻ tấn công chèn lệnh SQL.

#### Ví dụ về câu lệnh chuẩn bị Java an toàn
Trong ví dụ Java an toàn bên dưới, nếu kẻ tấn công nhập userID là `tom' or '1'='1`, truy vấn tham số sẽ tìm kiếm tên người dùng khớp với toàn bộ chuỗi `tom' or '1'='1`. Do đó, cơ sở dữ liệu sẽ được bảo vệ khỏi việc tiêm mã SQL độc hại.

Ví dụ mã sau đây sử dụng `PreparedStatement`, cách triển khai truy vấn tham số của Java, để thực thi cùng một truy vấn cơ sở dữ liệu.

```js
// This should REALLY be validated too
String custname = request.getParameter("customerName");
// Perform input validation to detect attacks
String query = "SELECT account_balance FROM user_data WHERE user_name = ? ";
PreparedStatement pstmt = connection.prepareStatement( query );
pstmt.setString( 1, custname);
ResultSet results = pstmt.executeQuery( );
```
#### Ví dụ về câu lệnh đã chuẩn bị C# .NET an toàn

Trong .NET, việc tạo và thực hiện truy vấn không thay đổi. Chỉ cần truyền tham số cho truy vấn bằng lệnh `Parameters.Add()` gọi như minh họa bên dưới.
```js
String query = "SELECT account_balance FROM user_data WHERE user_name = ?";
try {
  OleDbCommand command = new OleDbCommand(query, connection);
  command.Parameters.Add(new OleDbParameter("customerName", CustomerName Name.Text));
  OleDbDataReader reader = command.ExecuteReader();
  // …
} catch (OleDbException se) {
  // error handling
}
```

### Defense Option 2: Stored Procedures
Mặc dù Stored Procedures không phải lúc nào cũng an toàn trước SQL injection, các developer có thể sử dụng một số cấu trúc lập trình Stored Procedure chuẩn. Cách tiếp cận này có hiệu quả tương tự như sử dụng các truy vấn tham số, miễn là các Stored Procedure được triển khai an toàn (đây là chuẩn đối với hầu hết các stored procedure language).

#### Safe Approach to Stored Procedures
Nếu cần stored procedures, cách tiếp cận an toàn nhất để sử dụng chúng yêu cầu developer xây dựng các câu lệnh SQL với các tham số được tham số hóa tự động, trừ khi developer làm điều gì đó vượt quá chuẩn. Sự khác biệt giữa các câu lệnh đã chuẩn bị và stored procedures là mã SQL cho một stored procedure được định nghĩa và lưu trữ trong chính cơ sở dữ liệu, sau đó được gọi từ ứng dụng. Vì các câu lệnh đã chuẩn bị và stored procedures an toàn có hiệu quả như nhau trong việc ngăn chặn SQL injection.
#### Khi stored procedures có thể làm tăng rủi ro
Thỉnh thoảng, stored procedures có thể làm tăng rủi ro khi hệ thống bị tấn công. Ví dụ, trên MS SQL Server, có ba vai trò mặc định chính: `db_datareader`, `db_datawriter` và `db_owner`. Trước khi stored procedures được sử dụng, DBA sẽ cấp `db_datareader` hoặc `db_datawriter` quyền cho người dùng dịch vụ web, tùy thuộc vào yêu cầu.

Tuy nhiên, stored procedures yêu cầu quyền thực thi, một vai trò không có sẵn theo mặc định. Trong một số thiết lập mà quản lý người dùng đã được tập trung hóa, nhưng bị giới hạn ở 3 vai trò đó, các ứng dụng web sẽ phải chạy để `db_owner` stored procedures có thể hoạt động. Đương nhiên, điều đó có nghĩa là nếu máy chủ bị xâm phạm, kẻ tấn công có toàn quyền đối với cơ sở dữ liệu, trong khi trước đây, chúng chỉ có thể có quyền truy cập đọc.
#### Ví dụ về stored procedure Java an toàn
Ví dụ mã sau đây sử dụng triển khai giao diện stored procedures của Java ( `CallableStatement`) để thực hiện cùng một truy vấn cơ sở dữ liệu. `sp_getAccountBalance` stored procedures phải được xác định trước trong cơ sở dữ liệu và sử dụng cùng chức năng như truy vấn ở trên.
```js
// This should REALLY be validated
String custname = request.getParameter("customerName");
try {
  CallableStatement cs = connection.prepareCall("{call sp_getAccountBalance(?)}");
  cs.setString(1, custname);
  ResultSet results = cs.executeQuery();
  // … result set handling
} catch (SQLException se) {
  // … logging and error handling
}
```

### Defense Option 3: Xác thực đầu vào danh sách cho phép

Nếu gặp phải các phần truy vấn SQL không thể sử dụng bind variables, chẳng hạn như table names, column names, hoặc sort order indicators (ASC hoặc DESC), thì xác thực đầu vào hoặc thiết kế lại truy vấn là biện pháp phòng thủ phù hợp nhất. Khi cần tên bảng hoặc tên cột, lý tưởng nhất là các giá trị đó đến từ code  chứ không phải từ tham số người dùng.

#### Sample Of Safe Table Name Validation
CẢNH BÁO: Sử dụng giá trị tham số người dùng để nhắm mục tiêu tên bảng hoặc cột là một thiết kế kém và nên cân nhắc viết lại toàn bộ nếu thời gian cho phép. Nếu không thể, các dev nên ánh xạ các giá trị tham số vào tên bảng hoặc cột legal/expected ​​để đảm bảo đầu vào của người dùng chưa được xác thực không xuất hiện trong truy vấn.

Trong ví dụ bên dưới, vì `tableName` được xác định là một trong những giá trị hợp lệ và mong đợi cho tên bảng trong truy vấn này, nên có thể thêm trực tiếp vào truy vấn SQL. Lưu ý rằng các hàm xác thực bảng chung có thể dẫn đến mất dữ liệu nếu tên bảng được sử dụng trong các truy vấn không mong đợi.
```js
String tableName;
switch(PARAM):
  case "Value1": tableName = "fooTable";
                 break;
  case "Value2": tableName = "barTable";
                 break;
  ...
  default      : throw new InputValidationException("unexpected value provided"
                                                  + " for table name");


```
### Defense Option 4: RẤT KHÔNG ĐƯỢC KHUYẾN KHÍCH: Thoát khỏi mọi dữ liệu đầu vào do người dùng cung cấp

Trong cách tiếp cận này,  developer sẽ thoát khỏi mọi dữ liệu đầu vào của người dùng trước khi đưa vào truy vấn. Nó rất cụ thể về cơ sở dữ liệu trong quá trình triển khai. Phương pháp này yếu hơn so với các biện pháp phòng thủ khác và KHÔNG THỂ đảm bảo rằng tùy chọn này sẽ ngăn chặn mọi hành vi tiêm SQL trong mọi tình huống.

Nếu một ứng dụng được xây dựng từ đầu hoặc yêu cầu mức độ chấp nhận rủi ro thấp, thì ứng dụng đó phải được xây dựng hoặc viết lại bằng các truy vấn tham số, các thủ tục được lưu trữ hoặc một số loại Object Relational Mapper (ORM) xây dựng các truy vấn.

Ngoài việc áp dụng một trong bốn biện pháp phòng thủ chính, chúng ta cũng nên áp dụng tất cả các biện pháp phòng thủ bổ sung này để cung cấp biện pháp phòng thủ chuyên sâu. Các biện pháp phòng thủ bổ sung này là:
- Least Privilege
- Allow-list Input Validation
